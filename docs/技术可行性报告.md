# 画布 huabu · v1.0 技术可行性报告

> 对应指令第一步。作者:Claude(Opus 4.7)。日期:2026-04-23。
> 本报告不写正式代码,只给出可行性结论 + 最小化验证代码片段。读完回复"OK 开始"后进第二步。

## TL;DR(先读结论)

| 关键能力 | 结论 | 风险等级 |
|---|---|---|
| 同时采集屏幕 + 摄像头 + 麦克风 | ✅ 可行 | 🟢 低 |
| 两个 `MediaRecorder` 并行录制 | ✅ 可行 | 🟡 中(CPU/内存压力) |
| `ffmpeg.wasm` 做"上屏下人"合成 | ✅ 可行 | 🟡 中(速度慢 + 2GB 内存墙) |
| `File System Access API` 保存成片 | ✅ Chrome/Edge/Safari 支持,Firefox 降级 | 🟢 低 |
| `IndexedDB` 存 10 分钟双轨原片 | ✅ 配额充足(≈600MB) | 🟢 低 |
| **整体结论** | **v1.0 方案完全可行** | 🟡 主要风险是导出速度 + 部署需要 COOP/COEP |

**一句话:技术路径是通的。唯一要在部署阶段确认的是 —— 必须用能配 HTTP 头的静态托管(Vercel/Cloudflare Pages 可以,GitHub Pages 不行),不能让用户"下载 HTML 本地双击打开"。**

## 一、浏览器是否允许同时采集屏幕 + 摄像头?

**结论:允许,零冲突。**

`getDisplayMedia()` 和 `getUserMedia()` 是两个独立的 API,返回两个独立的 `MediaStream`。浏览器不限制同时调用。你现有的 `FuYou-ScreenCap.html` 第 662 行和第 1017 行已经同时在用这两个 API,证明在你电脑上没问题。

最小验证代码:
```js
const screenStream = await navigator.mediaDevices.getDisplayMedia({
  video: { frameRate: 30 },
  audio: true // 系统音,Chrome 支持,Mac 需要额外工具
});
const camStream = await navigator.mediaDevices.getUserMedia({
  video: { width: 1280, height: 720 },
  audio: true // 麦克风
});
// 两路 Stream 相互独立,可各自用于 <video> 预览或 MediaRecorder
```

**注意点:**
- 两次调用会弹**两个权限弹窗**(选屏幕 + 选摄像头)。UX 上要在"选择屏幕"按钮旁边加文案说明。
- macOS 系统音需要 BlackHole 或 Loopback 这类虚拟声卡。v1.0 不解决,只用麦克风音即可。

## 二、两个 MediaRecorder 能稳定并行录制吗?

**结论:能,但要注意 CPU 压力。**

`MediaRecorder` 的实例之间相互独立,浏览器没有数量上限。在一台普通 i5/M1 笔记本上,同时开 2 个 MediaRecorder 录 1080p@30fps 和 720p@30fps,CPU 占用大约 30-50%,不会丢帧。

最小验证代码:
```js
const screenRec = new MediaRecorder(screenStream, {
  mimeType: 'video/webm;codecs=vp9,opus',
  videoBitsPerSecond: 6_000_000, // 6 Mbps
});
const camRec = new MediaRecorder(camStream, {
  mimeType: 'video/webm;codecs=vp9,opus',
  videoBitsPerSecond: 2_000_000, // 2 Mbps
});

const screenChunks = [], camChunks = [];
screenRec.ondataavailable = e => screenChunks.push(e.data);
camRec.ondataavailable = e => camChunks.push(e.data);

// 同步启动(两个 start 之间的微小间隔 <1ms,后期不需要对齐)
screenRec.start(1000); // 每 1 秒切一个 chunk,避免内存堆积
camRec.start(1000);
```

**注意点:**
- 两路录制起始时间戳虽然接近,但严格意义上不对齐。v1.0 用单次 `start()` 几乎同步启动(误差 <1ms,人眼不可察)。v2.0 如果要做精确对齐,用 `WebCodecs` 自行控制帧。
- Safari 的 MediaRecorder 不支持 WebM,只能录 MP4。要做 codec 探测 + 回退。

## 三、ffmpeg.wasm 能否做"上屏下人"合成?

**结论:能。当前稳定版 `@ffmpeg/ffmpeg 0.12.x`,Core 约 30MB,多线程版 ~2x 速度。**

### 版本与体积

- `@ffmpeg/ffmpeg` 0.12.x(JS 包装层,<100KB)
- `@ffmpeg/core` 0.12.x(WASM 核心,**~30MB**,首次加载)
- `@ffmpeg/core-mt` 多线程版(需要 SharedArrayBuffer)
- `@ffmpeg/util` 提供 `fetchFile`、`toBlobURL` 工具

### "上屏下人"合成 FFmpeg 命令

用 `scale` + `pad` + `vstack` 三个滤镜组合:

```
ffmpeg -i screen.webm -i cam.webm \
  -filter_complex "
    [0:v]scale=1080:607,pad=1080:1080:0:236:black[top];
    [1:v]scale=1080:840[bot];
    [top][bot]vstack=inputs=2
  " \
  -c:v libx264 -preset fast -crf 23 \
  -c:a aac -b:a 128k \
  out.mp4
```

解释:
- 屏幕画面缩到 1080×607(保持 16:9),上下留黑边凑成 1080×1080 正方形作为"上屏"区
- 摄像头缩到 1080×840 作为"下人"区
- 垂直堆叠,输出 1080×1920 竖屏

### JS 侧最小 demo(ffmpeg.wasm 0.12.x API)

```js
import { FFmpeg } from '@ffmpeg/ffmpeg';
import { fetchFile, toBlobURL } from '@ffmpeg/util';

const ffmpeg = new FFmpeg();
const baseURL = 'https://unpkg.com/@ffmpeg/core-mt@0.12.x/dist/esm';

await ffmpeg.load({
  coreURL: await toBlobURL(`${baseURL}/ffmpeg-core.js`, 'text/javascript'),
  wasmURL: await toBlobURL(`${baseURL}/ffmpeg-core.wasm`, 'application/wasm'),
  workerURL: await toBlobURL(`${baseURL}/ffmpeg-core.worker.js`, 'text/javascript'),
});

await ffmpeg.writeFile('screen.webm', await fetchFile(screenBlob));
await ffmpeg.writeFile('cam.webm', await fetchFile(camBlob));

ffmpeg.on('progress', ({ progress }) => updateUI(progress));

await ffmpeg.exec([
  '-i', 'screen.webm',
  '-i', 'cam.webm',
  '-filter_complex',
  '[0:v]scale=1080:607,pad=1080:1080:0:236:black[top];[1:v]scale=1080:840[bot];[top][bot]vstack',
  '-c:v', 'libx264', '-preset', 'fast', '-crf', '23',
  '-c:a', 'aac', '-b:a', '128k',
  'out.mp4',
]);

const data = await ffmpeg.readFile('out.mp4');
const blob = new Blob([data], { type: 'video/mp4' });
```

### 性能预期

| 素材时长 | 单线程耗时 | 多线程耗时(mt) |
|---|---|---|
| 1 分钟 1080p 素材 | ~60-90 秒 | ~30-45 秒 |
| 5 分钟素材 | ~5-8 分钟 | ~2.5-4 分钟 |
| 10 分钟素材 | ~10-16 分钟 ⚠️ | ~5-8 分钟 |

**注意:** 超过 500MB 单文件在 ffmpeg.wasm 中有 OOM 风险(见第六节)。v1.0 先按"单次 10 分钟内素材"设计,超长素材放 v2 用 WebCodecs + 分段处理。

## 四、File System Access API 支持情况 + 降级方案

**结论:Chromium 系全支持,Safari 15.4+ 部分支持,Firefox 不支持(必须降级)。**

| 浏览器 | `showSaveFilePicker` | 降级方案 |
|---|---|---|
| Chrome 86+ | ✅ 完整 | 不需要 |
| Edge 86+ | ✅ 完整 | 不需要 |
| Safari 15.4+ | ⚠️ 部分(保存可用,部分高级 API 不支持) | 按需降级 |
| Firefox | ❌ 完全不支持 | `<a download>` 触发下载 |

**中国用户浏览器覆盖率估算:**
- 桌面端主流:Chrome、Edge、360、QQ、搜狗、百度 —— 绝大多数是 Chromium 内核,`showSaveFilePicker` 直接支持
- Safari(Mac 用户)—— 部分支持,回落到 `<a download>` 问题也不大
- Firefox —— 国内份额极低(<2%),直接走降级

### 降级策略(v1.0 直接实现)

```js
async function saveVideo(blob, suggestedName) {
  if ('showSaveFilePicker' in window) {
    try {
      const handle = await window.showSaveFilePicker({
        suggestedName,
        types: [{ description: 'MP4 Video', accept: { 'video/mp4': ['.mp4'] } }],
      });
      const writable = await handle.createWritable();
      await writable.write(blob);
      await writable.close();
      return;
    } catch (e) {
      if (e.name === 'AbortError') return; // 用户取消
      // 其他错误走降级
    }
  }
  // 降级:触发浏览器下载到默认下载文件夹
  const a = document.createElement('a');
  a.href = URL.createObjectURL(blob);
  a.download = suggestedName;
  a.click();
  URL.revokeObjectURL(a.href);
}
```

## 五、IndexedDB 能存多大?

**结论:配额充足,10 分钟双轨录制约 600MB,远小于浏览器限制。**

### 浏览器配额

- Chrome/Edge:最多可用**整个磁盘的 60%**,且每个 origin 可占用这个池子的大部分
- Safari:每个 origin 约 1GB,超出会主动提示用户
- Firefox:类似 Chrome 策略

### 录制体积估算

| 轨道 | 参数 | 1 分钟 | 10 分钟 |
|---|---|---|---|
| 屏幕 1080p@30fps | VP9 ~6 Mbps | ~45 MB | ~450 MB |
| 摄像头 720p@30fps | VP9 ~2 Mbps | ~15 MB | ~150 MB |
| **合计** | | **~60 MB** | **~600 MB** |

所以 v1.0 的典型使用场景(单次录制 ≤10 分钟)完全在配额内。长于 10 分钟的录制要在 UI 上提示"录制时间较长,导出耗时可能 >10 分钟"。

### 前置检查代码

```js
if ('storage' in navigator && 'estimate' in navigator.storage) {
  const { quota, usage } = await navigator.storage.estimate();
  console.log(`配额 ${(quota/1e9).toFixed(1)}GB,已用 ${(usage/1e6).toFixed(0)}MB`);
  if (quota - usage < 1e9) {
    showWarning('本地存储空间不足 1GB,建议清理浏览器缓存');
  }
}
```

## 六、已知陷阱 + 规避方案

### 坑 1:ffmpeg.wasm 需要 COOP/COEP 头才能多线程(最大的坑)

**问题:** ffmpeg.wasm 多线程版依赖 `SharedArrayBuffer`,浏览器为了安全要求跨域隔离,必须服务端返回:
```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

没有这两个头,只能跑单线程版,速度差一倍。而且 `file://` 协议(本地双击打开 HTML)完全不支持。

**规避:**
- 部署选 **Vercel**(免费、支持自定义 header via `vercel.json`)或 **Cloudflare Pages**(免费、`_headers` 文件配置)
- **不能用 GitHub Pages**(不支持自定义 header)
- 开发阶段用 Vite,加 `vite-plugin-cross-origin-isolation` 插件自动注入头
- 旧版"下载 HTML 文件双击打开"的用法**废弃**,v1.0 必须走 HTTPS

### 坑 2:ffmpeg.wasm 2GB 内存硬墙

**问题:** WebAssembly 单实例最多用 2GB(部分浏览器 4GB)。输入 + 输出 + 中间缓冲加起来超过这个数就 OOM 崩溃。

**规避:**
- v1.0 限制单次导出源素材 ≤ 500MB(约 15 分钟 1080p)。UI 上提示并阻止
- 导出前用 `navigator.deviceMemory` 判断设备内存,<4GB 的机器走单线程 + 低码率
- v2.0 用 WebCodecs 做流式处理,彻底绕开这个限制

### 坑 3:Safari MediaRecorder 不支持 WebM

**问题:** Safari 只能录 MP4/H.264,不认 WebM/VP9。

**规避:** 用 `MediaRecorder.isTypeSupported()` 探测,按优先级回落:
```js
const candidates = [
  'video/webm;codecs=vp9,opus',  // Chrome/Edge 首选,压缩率最好
  'video/webm;codecs=vp8,opus',  // 老 Chrome 兼容
  'video/mp4;codecs=h264,aac',   // Safari 唯一选项
];
const mimeType = candidates.find(t => MediaRecorder.isTypeSupported(t));
```

### 坑 4:getDisplayMedia 在不同浏览器上选项不同

**问题:**
- Chrome 能选"整个屏幕 / 窗口 / 标签页",还能带标签页音频
- Safari 只能选整个屏幕或窗口,没有标签页选项
- `cursor: 'always'` 参数在 Safari 被忽略

**规避:** 不依赖特定选项,UI 上按"能选什么选什么"引导用户。文案加一句"推荐用 Chrome 或 Edge 浏览器以获得最佳体验"。

### 坑 5:IndexedDB 大 Blob 写入慢 + 可能被浏览器淘汰

**问题:**
- 存入 500MB 以上的 Blob 时,Chrome 会卡 1-2 秒
- 用户磁盘空间吃紧时,浏览器可能主动清理 IndexedDB(非持久化存储时)

**规避:**
- 用 `navigator.storage.persist()` 请求持久化,防止被清理
- 录制时 MediaRecorder 用 `start(1000)` 每秒切 chunk,边录边写 IndexedDB(而不是录完一次写入)
- 录完立刻导出成品后,清空 IndexedDB 原片(除非用户想保留工程)

## 七、给用户的明确提示(v1.0 产品文案)

基于以上可行性分析,v1.0 需要在 UI 上明确告诉用户:

1. **浏览器推荐**:Chrome / Edge 为佳,Safari 可用,Firefox 暂不支持(无法保存文件)
2. **录制时长建议**:单次 ≤10 分钟体验最佳,最长 ≤15 分钟
3. **导出耗时预期**:素材 5 分钟,导出约 3-5 分钟,请耐心等待
4. **部署要求**:必须通过 HTTPS 访问(不能下载 HTML 本地打开)

## 八、下一步(第二步)的前置准备

进第二步前,需要你确认:

1. **部署选型**:Vercel 还是 Cloudflare Pages?(我建议 Vercel,对中文创作者最友好,也支持自定义域名)
2. **包管理器**:npm、pnpm 还是 yarn?(我建议 pnpm,速度快 + 节省磁盘)
3. **构建工具**:Vite(推荐,对 ffmpeg.wasm 支持成熟)

这三个确认后,第二步就是:搭 Vite 项目骨架 → 跑通最小录屏链路(选屏幕 → 录 10 秒 → 保存到本地)。
